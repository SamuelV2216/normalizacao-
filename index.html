Introdução

Vamos começar com uma situação comum: uma pequena loja controla os pedidos em uma planilha. Quando um cliente muda de telefone, a pessoa responsável precisa corrigir esse telefone em todas as linhas em que ele aparece. Se esquecer uma, o banco fica com informações diferentes para a mesma pessoa.

Neste artigo, vamos mostrar como transformar essa planilha em tabelas relacionadas usando a 1FN, a 2FN e a 3FN. Ao final, você vai entender o que é dependência funcional, chave primária, chave estrangeira e anomalia de dados.

Aprofundamento

Dependência funcional: um atributo B depende funcionalmente de A quando, conhecendo o valor de A, conseguimos determinar um único valor de B. Exemplo: o CPF determina o nome do cliente.

Chave primária: coluna, ou conjunto de colunas, que identifica de forma única cada linha de uma tabela.

Chave estrangeira: coluna que referencia a chave primária de outra tabela, criando a relação entre elas.

O problema: uma planilha que repete dados

Veja a tabela inicial da loja. Ela mistura informações de pedidos, clientes e produtos:

Tabela 1 — Planilha inicial de pedidos (dados fictícios)
ID pedidoClienteTelefoneProdutoPreçoQuantidade
1Ana Souza(11) 90000-0001Teclado150,001
2Ana Souza(11) 90000-0001Mouse80,002
3Bruno Lima(11) 90000-0002Monitor900,001

Essa estrutura causa três anomalias:

  • Inserção: não conseguimos cadastrar um novo produto sem ter um pedido.
  • Atualização: se o telefone da Ana mudar, precisamos alterar várias linhas.
  • Exclusão: se apagarmos o pedido 3, podemos perder a informação de que a loja vende monitores.

1FN: um valor por célula

Na Primeira Forma Normal, cada coluna deve guardar apenas um valor por linha. Não podemos colocar “Teclado, Mouse” em uma única célula nem criar colunas como produto1, produto2 e produto3.

No nosso exemplo, cada linha já representa um item de pedido, então a tabela está próxima da 1FN. Ainda assim, falta uma chave clara para cada item: a combinação de ID pedido e Produto pode identificar a linha.

Definição formal: uma relação está na 1FN quando todos os seus atributos contêm valores atômicos e não existem grupos repetitivos.

2FN: sem dependência parcial

A Segunda Forma Normal exige que a tabela esteja na 1FN e que nenhum atributo dependa apenas de parte de uma chave primária composta.

Se a chave for composta por id_pedido e id_produto, o nome e o preço do produto dependem somente do produto, não do pedido. Por isso, eles devem sair da tabela de itens.

-- SGBD usado: PostgreSQL 16
-- O nome e o preço pertencem ao produto,
-- e não ao par pedido + produto.
CREATE TABLE produtos (
  id_produto SERIAL PRIMARY KEY,
  nome VARCHAR(100) NOT NULL,
  preco NUMERIC(10,2) NOT NULL
);

O script completo, com criação e inserção de dados, está em sql/normalizacao.sql.

Definição formal: uma relação está na 2FN quando está na 1FN e todo atributo não-chave depende da chave candidata inteira, sem dependência parcial.

3FN: sem dependência transitiva

A Terceira Forma Normal exige que a tabela esteja na 2FN e que nenhum atributo não-chave dependa de outro atributo não-chave.

Na planilha original, o telefone depende do cliente, e não do pedido. Portanto, vamos separar os clientes em outra tabela:

-- O telefone depende do cliente,
-- e não do pedido.
CREATE TABLE clientes (
  id_cliente SERIAL PRIMARY KEY,
  nome VARCHAR(100) NOT NULL,
  telefone VARCHAR(20)
);

CREATE TABLE pedidos (
  id_pedido SERIAL PRIMARY KEY,
  id_cliente INT NOT NULL,
  CONSTRAINT fk_pedido_cliente
    FOREIGN KEY (id_cliente)
    REFERENCES clientes(id_cliente)
);

Definição formal: uma relação está na 3FN quando está na 2FN e nenhum atributo não-chave depende transitivamente da chave candidata.

Modelo final

Com a normalização, ficamos com quatro tabelas: clientes, pedidos, produtos e pedido_itens. A tabela pedido_itens liga um pedido a um produto e guarda a quantidade comprada.

CREATE TABLE pedido_itens (
  id_pedido INT NOT NULL,
  id_produto INT NOT NULL,
  quantidade INT NOT NULL CHECK (quantidade > 0),
  PRIMARY KEY (id_pedido, id_produto),
  CONSTRAINT fk_item_pedido
    FOREIGN KEY (id_pedido) REFERENCES pedidos(id_pedido),
  CONSTRAINT fk_item_produto
    FOREIGN KEY (id_produto) REFERENCES produtos(id_produto)
);

Esta consulta mostra o pedido completo sem repetir o telefone do cliente em cada item:

SELECT p.id_pedido,
       c.nome AS cliente,
       pr.nome AS produto,
       pi.quantidade,
       pr.preco
FROM pedidos p
JOIN clientes c ON c.id_cliente = p.id_cliente
JOIN pedido_itens pi ON pi.id_pedido = p.id_pedido
JOIN produtos pr ON pr.id_produto = pi.id_produto
ORDER BY p.id_pedido;

Se a Ana mudar de telefone, atualizamos apenas uma linha:

UPDATE clientes
SET telefone = '(11) 90000-0009'
WHERE id_cliente = 1;

Erros comuns

  • Colocar vários valores em uma célula: dificulta consultas e viola a 1FN.
  • Repetir o nome do cliente em cada pedido: gera anomalia de atualização.
  • Guardar o preço na tabela de itens sem necessidade: o preço normalmente pertence ao produto; se houver preço promocional por pedido, esse é outro requisito e deve ser modelado separadamente.
  • Normalizar sem analisar o contexto: em relatórios ou sistemas analíticos, alguma redundância controlada pode ser útil.

Por isso, não defendemos que todo banco deva ser normalizado até a 3FN sem análise. Em sistemas transacionais, a normalização costuma ajudar na consistência; em relatórios, pode ser interessante avaliar desnormalização controlada.

Decisões do grupo

  • Vamos usar PostgreSQL 16 porque é um SGBD relacional gratuito, bem documentado e amplamente usado no mercado.
  • Vamos explicar 1FN, 2FN e 3FN com um único caso de loja para manter o exemplo progressivo e fácil de acompanhar.
  • Vamos apresentar o problema antes da teoria porque o público-alvo já conhece SQL básico, mas tem pouca experiência com modelagem.
  • Não vamos incluir vídeos, pois preferimos concentrar o tempo na figura do modelo, no script SQL e na demonstração da anomalia corrigida.
